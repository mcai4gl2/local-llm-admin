## Optional Admin Login (ADMIN_AUTH_ENABLED)

### Problem/Goal
The admin requires a password login. The operator runs it only inside a trusted local network and wants the option to turn the login off.

### Problems Encountered
None. The private denylist for `scripts/check_public.py` was not present on this machine, so the leak scan could not run; the change adds placeholders only.

### Key Design Decisions
- Default stays secure: `admin_auth_enabled: bool = True`; `ADMIN_AUTH_ENABLED=false` opts out.
- When disabled, the session middleware injects a synthetic `{"csrf": ""}` session so page templates and `/api/session` keep working, and the CSRF check is skipped (no session cookie exists to protect).
- `/login` and `/logout` redirect to `/`; the base template hides the Log out button via an `auth_enabled` context flag.
- A startup warning in `admin.log` records the choice.

### Solution/Implementation
- `src/local_llm_admin/config.py`: new `admin_auth_enabled` setting.
- `src/local_llm_admin/app.py`: middleware bypass, login/logout redirects, `auth_enabled` in page context, startup warning log.
- `src/local_llm_admin/templates/base.html`: logout form conditional on `auth_enabled`.
- `tests/test_app.py`: `noauth_client` fixture and four tests (pages render without a cookie and without the logout form, API and `/api/session` work, POST needs no CSRF, `/login` and `/logout` redirect to `/`).
- `docs/DESIGN.md` §6 and deployment notes, `ops/env.example`: documented the option.

### Results
- `uv run pytest --cov --cov-fail-under=80`: 3911 passed, 4 skipped, total coverage 96.49%.
- `uv run ruff check src tests scripts`: all checks passed.
- `uv run mypy src scripts`: no issues in 70 source files.

## public-guard: Scan Only Introduced Commits

### Problem/Goal
The `public-guard` denylist job failed on every push: it ran `check_public.py --commits HEAD`, and `git rev-list HEAD` scans all reachable history, including an already-published merge commit whose immutable author metadata matches the private identity patterns.

### Problems Encountered
None. Verified the new ranges (`BASE..HEAD`, `HEAD^!`) locally against the repo with a dummy pattern.

### Key Design Decisions
- Scope the denylist commit scan to what each event introduces: `before..head` on push, `base..head` on PRs, just the head commit (`HEAD^!`) on dispatch or when no usable base exists.
- The full tracked tree is still scanned, and gitleaks keeps covering credentials across the full history.
- The script itself was already range-capable; only the workflow changed.

### Solution/Implementation
- `.github/workflows/public-guard.yml`: compute the commit range from `pull_request.base.sha` or `push.before`, fall back to `HEAD^!`.

### Results
- Local validation: YAML parses; both rev-list ranges resolve to the pushed commit only; `check_public.py` exits 0 with a dummy pattern.

### Files Modified
- `.github/workflows/public-guard.yml`
- `devlogs/2026-11-08.md`

## Lessons Learned
`git rev-list <sha>` means "everything reachable"; a history-scanning guard must receive an explicit range or it re-judges immutable published commits on every run.
